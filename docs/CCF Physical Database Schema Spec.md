# 3. UUID Specification

All major entities use UUID primary keys.

```text
id UUID PRIMARY KEY
```

UUIDs are generated by the database/ORM rather than manually supplied by users.

### UUID must never be exposed as a user-editable identifier.

Public event URLs use:

```text
/events/<slug>
```

rather than raw IDs.

---

# 4. Timestamp Specification

All timestamps:

```text
TIMESTAMPTZ NOT NULL
```

unless explicitly marked nullable.

Database storage:

```text
UTC
```

Application display:

```text
Asia/Kolkata
```

### Required timestamp fields

Most entities use:

```text
created_at
updated_at
```

with:

```text
created_at → DEFAULT CURRENT_TIMESTAMP
updated_at → updated by application/ORM
```

Event scheduling fields:

```text
registration_opens_at
registration_closes_at
starts_at
ends_at
```

remain nullable where the event does not require them.

# 6.12 `event_participants`

```text
id                      UUID PK

event_id                UUID FK
registration_id         UUID FK

participant_type        ParticipantType

college_normalized      VARCHAR(250) NULL
identifier_normalized   VARCHAR(100)

created_at              TIMESTAMPTZ
```

### Purpose

```text
EVENT_PARTICIPANT
    =
event-scoped active participant identity registry
```

It is **not** the source of detailed registration responses.

It exists primarily to enforce:

> A participant cannot have more than one active registration/participation in the same event.

### Foreign Keys

```text
event_id
    → events.id

registration_id
    → registrations.id
```

### Crescent uniqueness

```text
UNIQUE
    (event_id, identifier_normalized)

WHERE
    participant_type = CRESCENT
```

### External uniqueness

```text
UNIQUE
    (event_id, college_normalized, identifier_normalized)

WHERE
    participant_type = EXTERNAL
```

These will be implemented as **PostgreSQL partial unique indexes**.

### Relationship

```text
Individual Registration
    → 1 EventParticipant

Team Registration
    → N EventParticipants
```

# 7. Referential Actions

This is our physical FK policy.

## Registration-owned data

```text
registrations
    │
    ├── registration_responses
    ├── teams
    │      └── team_members
    ├── payments
    └── event_participants
```

These are dependent on a registration.

Therefore:

```text
Registration DELETE
        ↓
CASCADE dependent records
```

This makes controlled registration deletion safe.

---

## Event content

```text
events
    ↓
event_content
```

Can use:

```text
ON DELETE CASCADE
```

because event content has no independent meaning.

---

## Event participants

```text
registrations
    ↓
event_participants
```

Use:

```text
ON DELETE CASCADE
```

because deleting the registration must release the participant identity lock.

---

## Media

We should **not automatically delete media just because an event is deleted**.

Our event itself is normally archived, and media represents historical public content.

So media deletion should be explicit.

# 9. Critical Transaction Requirements

These aren't merely database constraints. They are **mandatory transactional operations**.

## Registration transaction

```text
BEGIN
    ↓
Validate event
    ↓
Validate event status
    ↓
Validate registration window
    ↓
Validate eligibility
    ↓
Lock/check capacity
    ↓
Check participant uniqueness
    ↓
Create registration
    ↓
Create responses
    ↓
Create team/team members if required
    ↓
Create event_participants
    ↓
Create payment record if required
    ↓
COMMIT
```

Any failure:

```text
ROLLBACK
```

# 10. Capacity Concurrency

This is critical for the expected ~500 registrations.

Example:

```text
capacity = 500
current = 499
```

Two requests arrive simultaneously.

We cannot allow:

```text
A → sees 499
B → sees 499

A → register
B → register

result = 501
```

Capacity enforcement must therefore occur inside a transaction with appropriate PostgreSQL locking/concurrency control.

# 11. Registration Purge Specification

When CCF requests deletion of an event's registration data:

```text
BEGIN TRANSACTION
```

Delete:

```text
registration_responses
team_members
teams
payments
event_participants
registrations
```

Then:

```text
AUDIT_LOG
    →
record purge operation
```

Finally:

```text
COMMIT
```

Retain:

```text
events
event_content
media
form_versions
event_fields
audit_logs
```

The event itself is **not deleted**.

# 12. Registration Reassignment

If a team disbands:

```text
Team A
    ↓
Registration cancelled/deleted
    ↓
EventParticipant locks released
    ↓
Members become eligible for another team
```

New team:

```text
Team B
    ↓
New registration
    ↓
New EventParticipant records
```

This means participant uniqueness is based on **active participation**, not permanent historical ownership.

# 15. Physical Schema Invariants

These are the rules that must remain true after implementation.

```text
1. Every registration belongs to exactly one event.

2. Every registration references a form version belonging to
   the same event.

3. A participant can have only one active participation
   in the same event.

4. Crescent uniqueness is based on:
   event_id + RRN.

5. External uniqueness is based on:
   event_id + college + roll_number.

6. A team registration has at most one Team record.

7. A team can contain multiple TeamMembers.

8. EventParticipant records represent active participation
   identity locks, not registration responses.

9. Payment belongs to at most one registration.

10. Published form versions are immutable.

11. Registration responses belong to one registration
    and one event field.

12. Event registration data can be purged without deleting
    the public event.

13. Purging registration data releases EventParticipant locks.

14. Public media is stored in Cloudflare R2;
    PostgreSQL stores metadata/object references.

15. Database timestamps are stored in UTC.

16. Capacity enforcement must be concurrency-safe.
```
